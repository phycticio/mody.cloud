## Repository layout

WordPress core and content are split Bedrock-style. Core lives in `app/wp`, content in `app/web`.

```text
.
├── app/                         # mounted at /var/www/html in the containers
│   ├── composer.json            # Composer root
│   ├── index.php                # front controller, loads wp/wp-blog-header.php
│   ├── wp-config.php            # configured from environment variables
│   ├── wp/                      # WordPress core (generated by ./bin/version, not tracked)
│   ├── web/                     # WP_CONTENT_DIR
│   │   ├── themes/theme/       # the FSE theme (the only tracked theme)
│   │   ├── plugins/             # Composer-managed, not tracked
│   │   ├── uploads/             # media, not tracked
│   │   └── db.php               # symlink to the Query Monitor drop-in
│   ├── dist/                    # pnpm build output (not tracked)
│   └── assets/                  # inherited from an earlier project, see local-development.md
├── bin/                         # helper scripts (wp, composer, certs, version, db, build, deploy, ...)
├── config/                      # Dockerfile, my.cnf, nginx/, php/, webpack/, bin/*.config
├── documentation/               # this documentation and the briefing PDF
├── src/                         # JS and SCSS sources for @wordpress/scripts
├── compose.yml                  # base stack
├── compose.local.yml            # local overrides (wildcard server_name, Xdebug build arg)
├── compose.*.yml.sample         # stage and production overrides
├── sample.env                   # copy to .env
├── wp-cli.yml                   # WP-CLI alias used by ./bin/wp
├── package.json, pnpm-lock.yaml # JS build with @wordpress/scripts
├── AGENTS.md, CLAUDE.md         # agent instructions
└── readme.md
```

`wp-config.php` sets `WP_CONTENT_DIR` to `app/web`, `WP_SITEURL` to `<home>/wp`, and `ABSPATH` to `app/wp/`. Nginx rewrites `/wp-admin`, `/wp-includes` and root `wp-*.php` requests into `/wp/`.

### Invariants that carry over from the briefing

- Only the web tier is public. The PHP-FPM container and the database are never reachable from the internet. Any proxy admin UI must be IP-restricted.
- `compose.yml` publishes Xdebug (`9003`) and MariaDB (`3306`) to the host for local work. `compose.prod.yml.sample` resets both and must be used in production. Production has used it since 2026-11-04.
- Credentials and Application Passwords never go into the repository, into logs or into prompts.
- The Nginx document root is `app/`, which also holds `auth.json` (Composer credentials), `composer.json`, `composer.lock`, `vendor/`, `logs/` and `dumps/`. `config/nginx/app.conf.template` denies those paths, all dotfiles except `/.well-known/`, and PHP under `web/uploads/`. Keep these rules when the template changes, and add any new non-public directory under `app/` to them.

### Multisite (enabled, M0-01)

Subdomain Multisite is on. `wp-config.php` reads `WORDPRESS_ALLOW_MULTISITE`, `WORDPRESS_MULTISITE` and `WORDPRESS_SUBDOMAIN_INSTALL`; `compose.yml` still defaults all three to `false`, and `sample.env` sets them to `true`. The wildcard `server_name` comes from `compose.local.yml` locally, and the wildcard certificate from `APP_DOMAINS` (`*.${HOST_NAME}`) via `./bin/certs`. In production the wildcard certificate for `*.mody.cloud` is terminated upstream; the briefing proposes a DNS challenge against Infomaniak DNS for it.

Two constants in `wp-config.php` deserve attention, because they are the pieces a subdomain network breaks on:

- **`DOMAIN_CURRENT_SITE` is `HOST_NAME`, always without a port.** `wp-includes/ms-settings.php` strips only `:80` and `:443` from the request host before looking the site up, so a host carrying any other port never matches `wp_site.domain` or `wp_blogs.domain` and every request ends on the `wp-signup.php` "site not installed" redirect. Requests therefore have to arrive on a standard port: either the stack's Nginx owns 443, or a proxy in front of it does and forwards the original `Host` header. `NGINX_HTTP_PORT` and `NGINX_HTTPS_PORT` are only where the container publishes itself on the host and must never reach a site URL.
- **`COOKIE_DOMAIN` is the main network domain**, which is what gives members the one shared login across all subdomains that the access model assumes ([mvp-spec.md](mvp-spec.md) §3). A `Domain` attribute covers subdomains even without a leading dot (RFC 6265 §5.2.3).

Where a proxy fronts the stack, it needs a server name covering `*.${HOST_NAME}` as well as the bare host, or only the main site answers over HTTPS and the subsites fail TLS on an unrecognised SNI name. Details and the local check are in [local-development.md](local-development.md#site-urls-never-carry-a-port).

### Deploying

**The deploy strategy** (decided by the maintainer on 2026-11-08):
1. Commit every change on its own topic branch, never directly on `main`. Name it after the work: `feature/m1-01-registration`, `fix/…`, `docs/…`.
2. Merge it into `main` locally with `git merge --no-ff`, so the branch stays visible in the history.
3. Push `main`. The repository's rule asks for pull requests; the maintainer's account bypasses it by choice, and GitHub reports the bypass on every push.
4. Deploy from `main` with `./bin/deploy --env=prod`.

Only the maintainer asks for a commit, push or deploy. The build needs the Node version in `.nvmrc` (22): a shell on nvm's default Node 20 fails in the JS step, before the server is touched.

```bash
git switch -c feature/<topic>          # 1. a branch per change
git commit …
git switch main && git merge --no-ff feature/<topic>   # 2. merge locally
git push origin main                   # 3. production deploys only pushed commits from main
./bin/deploy --env=prod --dry-run      # build, run every check, list what would change
./bin/deploy --env=prod                # the same, then type "prod" to sync
```

`bin/deploy` stops before it changes anything when one of these checks fails:

- The working tree has changes, the branch is not `main`, or `main` is not pushed. Only committed, shared code reaches production.
- SSH needs a prompt. Key authentication and a host key already in `known_hosts` are required (`BatchMode`, `StrictHostKeyChecking=yes`).
- The target is not the production stack. The script checks for `compose.yml` and `.env` in the directory, which also catches an unmounted disk, and for `HOST_NAME=mody.cloud`.
- The server's `app/composer.json` or `app/composer.lock` matches neither the commit being deployed nor the last deployed one (from `REVISION`). Then it was edited on the server, and the sync would delete what that edit added. A change made in the repository passes.
- The build fails, or it changes tracked files (for example the lockfile).
- The server's `app/web/plugins`, `app/web/mu-plugins` or `app/web/themes` has an entry the build does not, for example a plugin installed from wp-admin. Added after five wp-admin installs nearly got deleted on 2026-11-04.

Then it syncs an allowlist with `rsync --delete-after`: `app/`, `bin/`, `config/`, `compose.yml`, `compose.local.yml`, the two compose samples and `wp-cli.yml`. Server-owned files are excluded, so they are never sent and never deleted. Everything else stays on the developer machine: documentation, tickets, `src/`, `node_modules/`, `.git` and `backups/`. Older deploys copied some of those to the server. They are inert there and can be removed by hand.

The build runs `composer install --no-dev` in the local app container, so the local stack must be running. The script restores the local dev requirements when it ends. It does not restart containers. When `config/` or a compose file changes, it prints the command to run on the server: `docker compose up -d --build && docker compose restart nginx`. Nginx renders its templates only when it starts.

### Deviations to resolve

These are differences between production and the conventions above. None of them is fixed by a deploy. The steps for all three, and the decisions they need, are in [tickets/M5-02-production-member-sites.md](../tickets/M5-02-production-member-sites.md) (2026-11-08).

1. **Subsites cannot be reached.** There is no wildcard DNS record, and the NPM certificate and proxy host cover only `mody.cloud`. M2 needs `*.mody.cloud` (DNS, certificate and proxy host, as in [Multisite](#multisite-enabled-m0-01)). `www.mody.cloud` returns a Cloudflare 525 error, because the origin has no certificate for it.
2. **No outgoing mail.** PHP's `sendmail_path` (`config/php/sendmail.ini`) sends through msmtp to `mailpit:1025`. Mailpit never runs in production, so `wp_mail()` fails, and password resets and notifications are not delivered. Before 2026-11-04, Mailpit captured that mail and discarded it, which was also a loss, only a silent one. M1 needs real delivery for registration and billing emails. That means an EU SMTP relay (for example Infomaniak) configured in the production `.env` and PHP mail settings. Which relay to use is not decided.
3. **`home` carries `/wp`.** Both `home` and `siteurl` are `https://mody.cloud/wp`, so generated links read `https://mody.cloud/wp/sample-page/`. Both forms resolve, but the convention from M0-01 is `home` without `/wp`. Fix it with `wp option update home https://mody.cloud` after a database backup, then check the links stored in content. Until then, sites created by provisioning copy the main site's form (`Pipeline::urls()`), so production member sites get `siteurl` **without** `/wp` (`phycticio.mody.cloud`, seen 2026-11-07). That works, because nginx rewrites `/wp-admin/…`, `/wp-includes/…` and `wp-*.php` into `/wp/` on every host. After the fix, new sites get `/wp` like the local ones.

## Open questions

- **WordPress.org update checks and rule 1** (raised 2026-11-08, M4-02). Core asks `api.wordpress.org` for core, plugin and theme updates: on a WP-Cron timer, on admin page loads (twice a day at most), and on every load of the Plugins screen (at most hourly). This is not new and happens for every admin today, but since M4-02 members open the Plugins screen too. **Decided and built 2026-11-08** ([tickets/updates-through-composer-only.md](../tickets/updates-through-composer-only.md), [mvp-spec.md §10](mvp-spec.md#10-plugin-market-and-capability-gating)). Nobody updates WordPress or a plugin from wp-admin: `Gating\Updates` refuses the update capabilities to everyone. Core no longer checks on its own, so page loads never call WordPress.org for updates.
  - **Still calling it directly:** Wordfence's scans and activity report (they report outdated and vulnerable plugins), Site Health → Info, and WP-CLI run by hand.
  - **Still open:**
    - whether those direct calls stay, given rule 1;
    - how the maintainer hears about security releases, for example Wordfence's scan results, or `./bin/composer outdated` and `./bin/wp core check-update` run by hand;
    - the Dashboard's other WordPress.org calls: the Events and News widget, and the browser and PHP version checks. They are not update checks, and are not covered.
- **WP-Cron on subsites.** Docker's embedded DNS has no wildcard, so PHP in the app container cannot resolve `<slug>.${HOST_NAME}` and every loopback request from a subsite fails — WP-Cron spawning `wp-cron.php`, Site Health, REST calls between sites. Browser traffic is unaffected, because that path ends at Nginx and Nginx does have the wildcard `server_name`. `extra_hosts` is not a way out: Docker's `--add-host` takes an IP, not a service name, and one entry per site does not survive member-created sites. [mvp-spec.md](mvp-spec.md) §12 assumes WP-Cron is enabled and carries the hourly billing and sweep jobs, so this needs an answer before M1. The candidates are a static IP for the Nginx container plus generated `extra_hosts`, a `cron_request` filter in the MU plugin that posts to `http://nginx` with the target `Host` header (the pattern the agent service already uses), or `DISABLE_WP_CRON` with an external scheduler running `wp cron event run --due-now` per site. Workaround meanwhile: `./bin/wp --site=<slug> cron event run --due-now`. The agent chat does not depend on WP-Cron: its background jobs finish after the response with `fastcgi_finish_request()` ([ai-engine.md](ai-engine.md#background-jobs)).
- ~~**Per-site `theme.json`.**~~ Resolved (mvp-spec §7, built 2026-11-06 in M2-01): each site's identity goes through its own Global Styles (`wp_global_styles`), not a per-site file or a child theme. The briefing says the agent writes the site's `theme.json`; in Multisite all sites share one theme directory, so a per-site file is not possible.
- **Payments provider.** The briefing prefers Mollie ("more European") over Stripe. Stripe sits uneasily with the sovereignty rule. Decide in Milestone 3.2.
- **Where gating logic lives.** Likely a network-level plugin. Not specified.
- **Analytics.** Replacement for Matomo, if any.
- **Production host.** Production runs on a laptop with a USB disk, on a home connection shared with other projects. That is in Europe, so rule 1's location requirement holds, but it is not the European VPS the briefing assumes, and M5 needs a backup and restore drill. Decide whether to move to a VPS (Hetzner, Infomaniak) before launch. Replacing Cloudflare depends on this (see [Temporary exceptions to rule 1](#temporary-exceptions-to-rule-1)). Separately, the SSH alias `mody.cloud` in the maintainer's config points at a different Linux server, which does not serve the site (it answers 404 for `mody.cloud`). Its role is not documented.
