# Architecture

## Current stack (unchanged)

The infrastructure is the Docker stack already in this repository. The briefing's stack recommendations were deliberately not adopted (see below).

| Layer | Implementation | Defined in |
| --- | --- | --- |
| Web server | Nginx (alpine). Serves 80/443, proxies PHP to `wordpress:9000`. | `compose.yml`, `config/nginx/app.conf.template` |
| Application | Image built from the official `wordpress:${WORDPRESS_IMAGE_VERSION}` (PHP-FPM alpine). Adds gd, mysqli, pdo_mysql, zip, bcmath, exif, redis, msmtp, WP-CLI and Composer. | `config/Dockerfile` |
| Database | MariaDB 11.4.7 | `compose.yml`, `config/my.cnf` |
| Cache | Redis (alpine) container. No object-cache plugin is installed yet. | `compose.yml` |
| Mail (local) | Mailpit captures all outgoing mail, served at `MAIL_HOST` through Nginx. PHP sends through msmtp. | `compose.yml`, `config/nginx/mailpit.conf.template`, `config/php/` |
| Dependencies | Composer. WordPress plugins and themes install into `app/web/`. | `app/composer.json` |
| Dev tooling | Query Monitor (the only dev requirement) and its `db.php` drop-in symlink. | `app/composer.json`, `app/web/db.php` |
| Environments | `compose.yml` (local, mkcert TLS). Stage and production are compose overrides where TLS ends at an upstream proxy. | `compose.stage.yml.sample`, `compose.prod.yml.sample` |

## Repository layout

WordPress core and content are split Bedrock-style. Core lives in `app/wp`, content in `app/web`.

```text
.
├── app/                         # mounted at /var/www/html in the containers
│   ├── composer.json            # Composer root
│   ├── index.php                # front controller, loads wp/wp-blog-header.php
│   ├── wp-config.php            # configured from environment variables
│   ├── wp/                      # WordPress core (generated by ./bin/version, not tracked)
│   ├── web/                     # WP_CONTENT_DIR
│   │   ├── themes/theme/       # the FSE theme (the only tracked theme)
│   │   ├── plugins/             # Composer-managed, not tracked
│   │   ├── uploads/             # media, not tracked
│   │   └── db.php               # symlink to the Query Monitor drop-in
│   └── assets/                  # inherited from an earlier project, see local-development.md
├── bin/                         # helper scripts (wp, composer, certs, version, db, ...)
├── config/                      # Dockerfile, my.cnf, nginx/, php/, bin/*.config
├── documentation/               # this documentation and the briefing PDF
├── compose.yml                  # local stack
├── compose.*.yml.sample         # stage and production overrides
├── sample.env                   # copy to .env
├── wp-cli.yml                   # WP-CLI alias used by ./bin/wp
├── package.json, pnpm-lock.yaml # no JS dependencies at the moment
├── AGENTS.md, CLAUDE.md         # agent instructions
└── readme.md
```

`wp-config.php` sets `WP_CONTENT_DIR` to `app/web`, `WP_SITEURL` to `<home>/wp`, and `ABSPATH` to `app/wp/`. Nginx rewrites `/wp-admin`, `/wp-includes` and root `wp-*.php` requests into `/wp/`.

### Briefing recommendations not adopted

The briefing's stack section (§2) and Docker plus Nginx Proxy Manager section (§8) describe a different infrastructure. The current repository stack replaces it.

| Briefing recommendation | Decision |
| --- | --- |
| Nginx Proxy Manager as the TLS and proxy layer, with a proxy host for `mody.cloud` | Not adopted. The stack's own Nginx is used. Stage and production samples assume TLS ends at an upstream proxy, which can be NPM or anything else. |
| The sample `docker-compose` in §8 (stock `wordpress:latest`, `mariadb:10`, `mody_net`) | Superseded by `compose.yml`. |
| Matomo self-hosted container | Not part of the stack. Analytics is undecided. Whatever is chosen must be EU-hosted and GDPR-coherent. |
| Hosting description (single European VPS with a static IP, one A record) | Not prescribed. Only the sovereignty rule applies: servers in Europe or Switzerland. |

### Invariants that carry over from the briefing

- Only the web tier is public. The PHP-FPM container and the database are never reachable from the internet. Any proxy admin UI must be IP-restricted.
- `compose.yml` publishes Xdebug (`9003`) and MariaDB (`3306`) to the host for local work. `compose.prod.yml.sample` resets both and must be used in production.
- Credentials and Application Passwords never go into the repository, into logs or into prompts.

### Multisite (Phase 2)

`wp-config.php` already supports Multisite through environment variables: `WORDPRESS_ALLOW_MULTISITE`, `WORDPRESS_MULTISITE` and `WORDPRESS_SUBDOMAIN_INSTALL`. `compose.yml` defaults all three to `false`, so Phase 1 runs as a single site. Subdomain sites need a wildcard `server_name` in Nginx and a wildcard certificate. The briefing proposes a DNS challenge against Infomaniak DNS for that.

## Open questions

- **Per-site `theme.json`.** The briefing says the agent writes the site's `theme.json`. In Multisite all sites share one theme directory, so a per-site file is not possible. Per-site identity has to go through Global Styles stored per site, or a generated child theme per site. Decide in Milestone 2.3.
- **Payments provider.** The briefing prefers Mollie ("more European") over Stripe. Stripe sits uneasily with the sovereignty rule. Decide in Milestone 3.2.
- **Where gating logic lives.** Likely a network-level plugin. Not specified.
- **Analytics.** Replacement for Matomo, if any.
